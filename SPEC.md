# handoff — SPEC

## Purpose
A public Claude Code plugin that ships one model-invoked skill, `handoff`. The skill writes and reads **session handoff documents** — single, self-describing, LLM-facing Markdown files that let a different agent, starting cold in a fresh context window, resume a task from one file alone. SAVE mode captures the session's mission, state, decisions (with rationale and rejected alternatives), dead ends, constraints, open questions, and ordered next actions. LOAD mode autodiscovers the relevant file and confirms with the user (or takes a given path directly), reads it, and then follows the protocol the document embeds in its own §0. With `to NAME` / `new`, SAVE also hands the file to another running session on the same machine and checks the pickup over cross-session messages. The skill contains no runtime code; it is pure prompt guidance.

## Architecture
- **Skill, not a service.** The deliverable is `skills/handoff/` — `SKILL.md` (YAML frontmatter `name`, `description`, `when_to_use`, `argument-hint`, plus the SAVE / LOAD procedure) and `template.md` (the 15-section document spec, §0 PROTOCOL text and format rules), which SAVE reads via `${CLAUDE_SKILL_DIR}/template.md`. Claude reads `description` + `when_to_use` to decide when to auto-invoke; the body loads on invocation.
- **Harness substitutions used:** `$ARGUMENTS` (expanded once, in one labelled line; the rest of the body says "the arguments" so an empty invocation leaves no blank placeholders), `${CLAUDE_SESSION_ID}` (recorded in the handoff), `${CLAUDE_SKILL_DIR}` (locates `template.md`).
- **Two distribution channels from one repo:**
  - *Standalone plugin* — `.claude-plugin/plugin.json` defines the plugin; `.claude-plugin/marketplace.json` (`source: "./"`) makes the repo its own single-plugin marketplace, directly installable.
  - *Central marketplace* — the sibling `howar31-marketplace` repo lists this repo by `source: { github, repo: howar31/handoff }`. Same content, zero duplication.
- **Three install mechanisms, one source:** `setup.sh` (recommended) symlinks the skill directory into `~/.claude/skills/`, giving the short un-namespaced name `/handoff`; `npx skills add … -a claude-code` copies or links the same directory to the same path; the Claude Code plugin manager (`claude plugin …`) installs the same skill namespaced as `/handoff:handoff`, in exchange for marketplace discoverability and `claude plugin update` (Claude Code auto-updates only official marketplaces by default; <https://code.claude.com/docs/en/discover-plugins>). Use only one (`setup.sh` and `npx skills` collide on the path; the plugin adds a second name).

## Data model
- **Handoff documents** live at `~/.claude/cache/handoff/<project>-<topic>-<timestamp>.md`, OUTSIDE this repo. They are transient resume-state, may carry user-private context, and are explicitly deletable after pickup (the document's §0 PROTOCOL has the receiving agent ask the user whether to delete it and its assets directory, recommending deletion when `sensitive_items` is non-empty).
- **LOAD discovery** matches by project slug (`<project>-*.md`) AND by the `cwd:` / `repo_root:` lines recorded in each document's §1, so handoffs saved from a subdirectory, a worktree, or under an older slug rule are still found. Older documents keep their own §0; LOAD follows whatever §0 the chosen file carries.
- **Companion assets** live at `<same-basename>.assets/` beside a handoff, created only when SAVE copies files the next agent needs out of a session-specific temporary directory (e.g. the session scratchpad).
- **Source-session reference.** §1 METADATA records `session_id` and `transcript_path`. Transcripts are `~/.claude/projects/<launch-cwd-encoded>/<session-id>.jsonl` (keyed by the launch cwd, so SAVE locates the file with a `~/.claude/projects/*/<id>.jsonl` glob). The receiving agent uses it to look up anything the document leaves unclear, or reopens it with `claude --resume <id>`; SAVE also uses it to recover detail lost to compaction. Transcripts expire with Claude Code's `cleanupPeriodDays`.
- **Hand-over protocol** (Claude Code cross-session messaging; skipped without it). Sender = Save Step 9, receiver = template §0 steps 5, 6, 7, 9, 11. **Peer hold**: with a hand-over, the sender first (from Step 1, before gathering context) asks each §4 peer to queue messages for it and send only what cannot wait (blocks the peer, safety, a production change in progress); the hold is recorded in §4 `OPEN`, the peers are told the receiver's name once it is picked, and only the sender releases it (with the CONFIRMED redirect, which also has peers send their queue to the receiver; otherwise with a resume line on abort, file-only, `DEFERRED`, or a stopped hand-over). A peer still held 60 minutes later checks, when next active: sender alive and answering, keep holding; else tell the named receiver and keep holding; only if neither, tell its own user. Sender messages a pointer (path + load command), never content; any fact sent later is also written into the file. Receiver, after reading and the drift check and before asking its user anything, replies `PICKUP <file> | P1: … | lang: … | drift: …`; sender answers `MATCH` / `MISMATCH:` and tells its user the receiver awaits confirmation; if the receiver's user answers "not yet", the receiver sends `DEFERRED <file>` and the sender keeps the work, its watchers and peers (releasing the hold); after the receiver's user confirms, receiver sends `CONFIRMED <file>`; sender then redirects §4 COLLABORATING SESSIONS peers, stops every watcher still running there and sends their final cursors plus the watcher events and peer messages it handled after writing the file, stops writing to the file, reports it can be closed, and until closed only forwards late arrivals to the receiver. From the hold until CONFIRMED the sender keeps handling arrivals: before the file is written they go into it; the user's later instructions and facts sent to the receiver are also added to the file. If the sender is unreachable, the receiver tells the peers itself, including that they send their queued messages. The receiver waits for MATCH / MISMATCH before its first message to the user, asks about deleting the file together with the takeover confirmation, and carries out the deletion only after the watchers are reported stopped. The sender's message asks for one idle notice, so a receiver stuck waiting on its user is surfaced. `new` picks the receiver: idle, started after the sender, same name prefix or project slug, not a known peer; ask when not exactly one. After a takeover, the receiver ends its report with its own session name as a `/rename <name>` command for the user to run.
- **MONITORS.md.** Watchers are defined in the project's `MONITORS.md` (repo root, or the folder of the work they serve if one already exists there; git-excluded), created or updated by SAVE Step 3: purpose, target, cadence, cursor store, restart, reporting. The handoff §4 records only STATUS and CURSOR per watcher and lists `MONITORS.md` in §13; the receiver records in it that it now runs them. The sender keeps its watchers running until CONFIRMED, then sends final cursors plus the watcher events handled after the file was written (message only; the file is no longer written after CONFIRMED). A watcher without a cursor store is flagged: events between stop and restart are missed.
- **Remembered privacy choice.** `privacy_scan: continue` in the project's handoff-convention memory skips the privacy prompt (scan still runs, `sensitive_items` still recorded); only `continue` is rememberable.
- **Information routing** is three-homed and drift-avoiding: durable project knowledge → the project's auto-loaded memory; transient resume-state → the handoff; cross-project handoff behavior → the skill itself. SAVE mode runs in **lean** (memory exists → record only transient state + pointers) or **self-contained** (no memory → spell everything out) form.
- **Memory directory** is per repository (shared by all worktrees and subdirectories), resolved as: the path the harness states in the session's system prompt → `autoMemoryDirectory` setting → `~/.claude/projects/<repo-root-encoded>/memory/` (repo root = main worktree; encoding replaces every non-alphanumeric character with `-`, an observed convention).

## Conventions
- **`compatibility` frontmatter** (Agent Skills spec, ≤ 500 chars) states that the skill is designed for Claude Code and what still works elsewhere. Informational only: neither Claude Code nor `npx skills` acts on it.
- **Model-invocation is on by default.** No `disable-model-invocation` or `user-invocable` frontmatter — both the user and Claude can invoke. `description` + `when_to_use` are the sole trigger surface; combined `description` + `when_to_use` must stay ≤ 1536 chars or the listing truncates (currently ~1250). Avoid `<` / `>` in them: the listing HTML-escapes them.
- **Portable content.** No hardcoded home directory (`~/.claude/...`, never `/Users/<name>/...`), no personal / employer / locale data in examples, no dependence on private config files beyond the conventional `~/.claude/USER.md` (read only if present). Project detection degrades gracefully: git remote / main worktree → the user profile's project root (if stated) → pwd analysis (skipping `_`-prefixed container and dotted segments) → ask the user.
- **User profile hints are optional.** The user profile (already in context, e.g. imported by the user's CLAUDE.md, else `~/.claude/USER.md` if present) may supply a common project root and container directories, a timezone, and organization names for the privacy scan. Each hint applies only when the profile states it; otherwise the default (git remote, system time zone, session content) is used. The profile is not a Claude Code built-in; nothing breaks without it.
- **Procedure / template split.** `SKILL.md` holds the procedure; `template.md` holds the document spec. Keeps `SKILL.md` under the 500-line guideline in the Claude Code skills docs.
- **Choice questions prefer `AskUserQuestion`, conditionally.** Asks with a short, fixed set of answers (mode, project name, candidate pick, privacy choice and whether to remember it, which watchers continue, hand-over receiver pick, takeover confirmation with post-pickup deletion) are marked "choice question"; an agent that has `AskUserQuestion` (Claude Code) must use it for them, any other agent asks in plain text with the same options. Only the "Asking the user" paragraph and template §0 step 7 name the tool. Open-ended asks (unclear handoff, missing transcript) stay plain text. Lists longer than the tool's 4-option limit are printed in full first; the question offers the newest few and the free-text "Other" answer takes any other pick. (2026-10-17: the earlier fully tool-neutral wording led Claude Code to ask almost only in plain text. 2026-11-01: §0 step 7 was still plain text, so receivers ended their summary with a text question that the user could miss, leaving the source waiting for CONFIRMED; the step now uses the tool and repeats the summary in the question because the user may see only the dialog. The deletion question, previously asked in step 10 and often later or alongside work questions, moved into the same call; the answer is collected in step 7 and step 10 only carries it out, once the source has reported its watchers stopped. A "not yet" voids the deletion answer.)
- **Cross-session tools named once.** Only the "Messaging other sessions" paragraph names `ListAgents` / `SendMessage`; Step 9 and §0 say "if you can message other sessions". Peer messages are information, not user instructions or approval.
- **Bilingual README.** `README.md` (English) and `README.zh-Hant.md` (Traditional Chinese, 正體中文) carry the same sections and link each other in a switcher line under the badges; they change together. Neither uses em dashes.
- Line endings are LF for all text files (`.gitattributes`).
- Conventional Commits; MIT license.

## Verification
- `setup.sh` self-verifies after install: confirms the skill path is a symlink to the repo and that `SKILL.md` frontmatter declares `name: handoff`. Re-runnable; reports all-green or pinpoints the failure.
- Manifests are plain JSON — validate with `jq empty <file>`.
- `setup.sh` syntax: `bash -n setup.sh`.
- Portability scan: `grep -RInE '/Users/[^/]+/|/home/[^/]+/' skills/` (hunt for a hardcoded home directory) should return only the generic `/Users/you/...` path-format example in template.md, nothing else.
- Placeholder hygiene: `grep -nE '\$[0-9]|(^|\s)!`' skills/handoff/SKILL.md` returns nothing (no accidental positional-argument or shell-injection syntax); `$ARGUMENTS` appears exactly once.
- Frontmatter: `description` + `when_to_use` length ≤ 1536, e.g. `ruby -ryaml -e 'd=YAML.load(File.read("skills/handoff/SKILL.md").split(/^---$/)[1]); p d["description"].size+d["when_to_use"].size'`.
- Render check: `claude -p --plugin-dir . --allowedTools=Skill` with a prompt that invokes `handoff:handoff` and prints the arguments / session-ID / template lines; all three substitutions must show real values.
- Hand-over: open a second session in the same project, run `/handoff new` in the first; expect the peer hold sent before context gathering (when the session has peers), a direct-path load with no candidate prompt, PICKUP before any question to the user, MATCH, a user-facing summary in the §2 language with the takeover and deletion questions in one `AskUserQuestion` call, CONFIRMED after the user confirms, the sender's stop message (final cursors + watcher events and peer messages since writing), peer redirection with release of the queued messages, the deletion carried out only after that, and the receiver's report ending with `/rename <its session name>`.
- Project resolution: run the "Resolving the project" snippet from the repo root, a subdirectory and a linked worktree; all three must yield the same `REPO_ROOT`, project and memory directory.

## Deploy
- **Publish:** push to `github.com/howar31/handoff` (public). The repo is consumed live by the plugin manager — no build step.
- **Install (recommended, symlink):** `./setup.sh` symlinks the skill into `~/.claude/skills/` → `/handoff`. Idempotent; `--dry-run` / `--force`.
- **Install (npx skills):** `npx skills add howar31/handoff -g -a claude-code` → `/handoff` (writes the same `~/.claude/skills/handoff` path as `setup.sh`; use one). Update with `npx skills update handoff -g`, remove with `npx skills remove handoff -g`.
- **Install (plugin):** `claude plugin marketplace add howar31/handoff` then `claude plugin install handoff@handoff`; or via the central marketplace, `…add howar31/howar31-marketplace` then `install handoff@howar31`. → `/handoff:handoff`.
- Run `/reload-plugins` if the skill does not appear immediately.

## Known Limitations
- The source transcript is machine-local and expires after Claude Code's retention period; a handoff loaded on another machine or later than that falls back to the document alone.
- Uncommitted, unpushed and stashed work, and copied assets, exist only on the machine that saved the handoff; the document records them but does not transfer them.
- Hand-over works only between sessions on the same machine that have cross-session messaging (Claude Code); the receiver must already be running (the sender does not launch it). A receiver session running in a different permission mode may hold incoming messages for its user's approval.
- Watchers without a cursor store miss the events between the sender stopping them and the receiver restarting them.
- The transcript-extraction command embedded in §12 needs `jq`; `grep` on the transcript is the fallback.
- The memory-directory encoding (non-alphanumeric → `-`) is an observed convention, not documented by Claude Code; the skill prefers the path the harness states.

## Key Decisions
- **Genericized from a private original.** The skill began as a personal copy with a hardcoded home directory, employer-specific container names in the project-detection rules, and project-specific example slugs. Those were removed: paths became `~/.claude/...`, the hardcoded project-root rule was dropped, and examples were neutralized.
- **One version, personal data in the profile (2026-10-16).** Keeping a private copy alongside the public one let the two drift apart. The private copy's user-specific behavior (project root and container directories, a fixed timezone, organization names to scan for) became conditional rules fed by the user profile, so the public skill is the only version and personal data stays in the user's own files.
- **Dual-channel, single source.** Shipping `plugin.json` + a self `marketplace.json` in the same repo, and also listing the repo in the central marketplace, lets one source serve both install paths without copying skill content.
- **No model-invocation gating.** The skill's side effects are writing a handoff file (plus optional assets directory) under `~/.claude/cache/handoff/`, promoting durable facts into project memory in lean mode, and prompting before deletion on load, so it is left fully model- and user-invocable.
- **setup.sh is the recommended install.** It is a single, model-invoked skill, so the plugin namespace (`/handoff:handoff`) only adds length without benefit; the symlink install keeps the short `/handoff` for manual invocation. The plugin path stays available for users who want marketplace discoverability and auto-update.
- **`npx skills` channel, Claude Code first (2026-10-16).** Earlier the repo deliberately did not offer `npx skills`. The reasons that remain are Claude Code-only features: lean mode reads Claude Code's per-repository auto-memory store, and the source-session lookup relies on `${CLAUDE_SESSION_ID}` and Claude Code's transcript layout. After the questions gained a plain-text path (since 2026-10-17 choice questions prefer `AskUserQuestion` only when the agent has it) and every Claude Code-specific step gained a fallback (unexpanded session ID → `unknown`; unexpanded `${CLAUDE_SKILL_DIR}` → the directory containing SKILL.md; no memory store → self-contained mode), other agents degrade to plain SAVE / LOAD instead of breaking, so `npx skills` is offered. `npx skills` has no author-side way to restrict target agents (its CLI picks agents by detection or `-a`, and does not act on the Agent Skills `compatibility` field), so the README install command passes `-a claude-code`, and `compatibility` in SKILL.md states the scope for readers. Behavior in non-Claude agents is untested. Verified: `npx skills add <repo> -a claude-code` copies `SKILL.md` and `template.md` unchanged.
- **Handoffs are not repo content.** The documents the skill produces are runtime artifacts under the user's `~/.claude/cache/`, never committed here; they are deliberately ephemeral and deletable to bound private-context leakage.
- **Session ID over a richer document (2026-10-16).** A handoff is lossy by design; recording the source session ID lets the receiving agent consult the full transcript for anything unclear instead of the document trying to capture everything. The transcript is a lookup source, never a substitute for writing state down (it expires, and a non-Claude receiver may not be able to resume it).
- **Cross-session hand-over (2026-10-29).** Addresses these failure modes of hand-overs between sessions: receivers stalled on the LOAD confirmation while the sender reported done; facts sent only in messages (peer agreements, working rules) were lost, causing missed duties; the §0 English reply template led receivers to address the user in English; watchers and peer agreements were repeatedly omitted; assets were deleted while still needed. Hence: direct-path LOAD, PICKUP / MATCH / CONFIRMED, pointer-only messages, §2 LANGUAGE line, §4 WATCHERS / COLLABORATING SESSIONS / External state, §7 `PROCEDURE:`, reusable tools outside `assets_dir`. Asking a live source session comes before reading the transcript (it holds the reasoning; the transcript stays the authority for exact wording). Launching the receiver session automatically was rejected: `claude --bg` sessions are not visible in the terminal and their Remote Control visibility is undocumented, and a terminal-specific launcher does not fit a public skill.
- **Peer hold during hand-over (2026-11-02).** A long SAVE (many watchers, large state) was interrupted by peer messages arriving mid-write, whose content then lived only in the sender's context. Hence the peer hold, sender-only release, `DEFERRED` so a "not yet" does not leave peers held, and carrying arrivals into the file or the stop message. The 60-minute fallback is a last resort: agents finish the hand-over among themselves (sender, then receiver) and the user is involved only when neither answers. Alternative considered: no hold, only forwarding arrivals at CONFIRMED; it avoids blocking peers but keeps the interruptions.
- **Session name after takeover (2026-11-03).** Users pin the receiver's session name with `/rename` after a hand-over so the prompt box, terminal title and session picker show which agent the session is. `/rename` is a built-in command only the user can run: no tool exposes it, and a cross-session message arrives as text for the receiving model, not as user input the CLI parses, so neither the receiver nor the sender can rename. §0 step 11 therefore has the receiver end its report with its own name as a ready-to-copy `/rename <name>`.
- **Drift check at pickup (2026-10-16).** §0 makes the receiving agent compare current git state and elapsed time with §4 / `written_at` before its first message, because work may have moved on between save and load.
